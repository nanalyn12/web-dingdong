# TDD Cycle — dingdong

이 저장소에서 Red → Green → Refactor를 실행하는 구체 절차.

## 실행 명령

| 목적               | 명령                                       |
| ------------------ | ------------------------------------------ |
| 전체 유닛 테스트   | `npx vitest run`                           |
| 특정 파일          | `npx vitest run src/lib/vocab-srs.test.ts` |
| 워치 모드(개발 중) | `npx vitest`                               |
| 타입체크           | `npx tsc --noEmit`                         |
| lint               | `npm run lint`                             |
| 자동 서식 수정     | `npx eslint --fix <바꾼 파일들>`           |
| 프로덕션 빌드      | `npm run build`                            |
| 게이트 전체        | `npm run verify`                           |

앞의 셋(vitest·tsc·lint)이 L1, 빌드가 L2다. 네 개가 전부 통과해야 작업을 마쳤다고 말할 수 있다.

lint는 저장소 전체를 대상으로 하고 기준선은 **errors 0**이다. 서식 오류가 났다면 손으로 맞추지 말고 `npx eslint --fix`로 바꾼 파일만 정리한다.

## Red — 실패를 먼저 본다

1. 합격 기준 한 줄을 테스트 한 케이스로 옮긴다.
2. 실행해서 **실패를 확인한다.** 실패를 보지 않은 테스트는 검증력을 증명하지 못한 테스트다. 통과했다면 그건 이미 구현돼 있거나, 테스트가 아무것도 주장하지 않는 것이다.
3. 실패 출력을 그대로 기록한다.

```ts
// src/lib/vocab-srs.test.ts
import { describe, expect, it } from "vitest";
import { nextInterval } from "./vocab-srs";

describe("nextInterval", () => {
  it("오답이면 간격이 1일로 초기화된다", () => {
    expect(nextInterval({ interval: 21, correct: false })).toBe(1);
  });
});
```

## Green — 최소 구현

- 테스트를 통과시키는 **가장 단순한 코드**를 쓴다. 미래를 위한 일반화는 다음 테스트가 요구할 때 한다.
- **테스트 파일을 고쳐서 통과시키지 않는다.** 기준이 틀렸다면 기준을 명시적으로 재협상하고 이력에 남긴다. 조용히 낮춘 기준은 다음 iteration에서 또 낮아진다.
- 통과시키려고 입력값을 분기하는 하드코딩밖에 방법이 없다면, 기준이 잘못 쓰인 것이다. 보고한다.

## Refactor — 통과를 유지하며 정리

- 합격 기준은 그대로 두고 코드 형태만 바꾼다.
- 리팩터 후 반드시 게이트를 다시 돌린다. "고치기 전에 통과했으니 괜찮다"는 근거가 아니다.

## 무엇을 테스트하는가

**테스트한다 (L1 대상):**

- 순수 계산 로직 — SRS 간격, 진도율, 레벨 판정, 퀴즈 정규화, 태그 분류, 쿼터 산정
- 문자열·데이터 변환 — 병음 처리, 자막 파싱, 스키마 정규화
- 암호화/인코딩 왕복 — seal/open 같은 대칭 연산
- 순수 헬퍼로 분리 가능한 검증 로직 — env 스펙 검사 등

**테스트하지 않는다 (현재 게이트 범위 밖):**

- DB에 붙는 서버 함수, 외부 API 호출(Gemini·Suno·Pexels·TTS), ffmpeg 실행
- React 컴포넌트 렌더링, 라우팅, 브라우저 동작

경계선은 "외부의 변하는 상태에 의존하는가"다. 저장소에 체크인된 정적 파일을 읽는 것은 결정적이므로 허용된다 — `env.server.test.ts`가 `.env.example`과 스펙의 동기화를 검사하는 것이 그 예다.

범위 밖 코드는 **경계면 교차 검증**(`interface-crosscheck`)과 L2 빌드로 커버한다. 테스트하고 싶은 로직이 DB 호출 안에 섞여 있다면, 순수 함수로 떼어내는 것이 먼저다 — 그게 테스트 가능한 설계다.

## 테스트 작성 규칙

- 파일 위치: 대상 파일 옆. `src/lib/x.ts` → `src/lib/x.test.ts`
- 이름은 조건과 기대를 한국어로: `it("빈 배열이면 0을 반환한다")`
- 한 케이스 한 주장. `expect`가 5개를 넘으면 쪼갠다.
- 기대값은 상수로 직접 쓴다. 구현의 계산식을 테스트에서 다시 쓰면 둘이 같이 틀려도 통과한다.
- 경계값·빈 입력·잘못된 입력을 반드시 포함한다. 정상 경로만 있는 테스트 묶음은 회귀를 못 잡는다.
- 시간에 의존하는 로직은 `Date`를 인자로 주입받게 만들고, 테스트에서 고정 날짜를 넘긴다.

## 신규 vs 기존 코드

- **신규 기능**: 반드시 Red부터. 예외 없다.
- **기존 코드 수정**: 고치기 전에 현재 동작을 고정하는 테스트(characterization test)를 먼저 쓴다. 그래야 수정이 의도한 것만 바꿨는지 알 수 있다.
- **버그 수정**: 버그를 재현하는 실패 테스트를 먼저 쓴다. 그 테스트가 회귀 방지선이 된다.
